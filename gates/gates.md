# Design Gates — generic library (prumo, v0)

Design-reasoning gates, derived from the anti-patterns in `docs/method-patterns.md` and generalized.
They are **problem-agnostic** (they do not contain the answer to any video). Each gate has:
the principle, the **RED** condition, the skill it forces, and the layer (DET = checkable
over the graph/arithmetic; ADV = adversarial verifier run by a sub-agent).

Usage: run them against the `(requirements.json, design.json)` of a version; each RED becomes
a refinement item for the next version (v1→v2→…). Green on all of them = you can stop.

| id | principle | RED when | skill | layer |
|---|---|---|---|---|
| G-REQ-COMPLETENESS *(runs in the requirements phase, before the design)* | the requirements cover the implicit surface of the problem (entities, actions, relationships, edge cases, invariants) and each NFR comes from the shape of the workload | a functional requirement/relationship/invariant that the domain clearly implies is missing, or an NFR is not tied to the workload, or the requirements echo the problem statement without derivation | elicit-requirements-from-intent | ADV |
| G-AMPLIFICATION | when materializing a property by fan-out (1 write per affected entity), compute the post-amplification write TPS and re-test the read:write ratio | there is fan-out/materialization and the post-amplification write TPS **was not computed**, or it was and the ratio became write-heavy without a change of engine | find-the-binding-constraint | DET+ADV |
| G-CAPACITY | translate the binding bottleneck into a concrete number of machines/partitions; the design's capacity ≥ the required capacity | the bottleneck→machines calculation is missing, or the summed capacity < the required QPS/throughput | find-the-binding-constraint | DET |
| G-NO-REINVENT | once a specialized processor (stream/engine) is chosen, do not reintroduce a store+merge that duplicates what it already does | there is a specialized stream/engine **and** a redundant counter/merge without justification | iterate-naive-to-optimal | ADV |
| G-FREETEXT | add an inverted index/search engine only if the query really is full-text | there is a search engine for a query that is equality/term/range | choose-datastore-by-access-pattern | DET+ADV |
| G-IDEMPOTENT | an external call with a side effect must be preceded by persisting an idempotency key | an edge to an `external` with a side effect and no persist before it | design-for-partial-failure | DET |
| G-UNIQUENESS | uniqueness/exactly-once requires a linearizable store, not an eventual one | a uniqueness requirement whose write path ends in a store with `consistency=eventual` | design-for-partial-failure | DET |
| G-ORDERING | order the steps so the irreversible action comes last / the failure is the least-bad one | an irreversible step (charge, dispatch) before the dependency that justifies it | design-for-partial-failure | ADV |
| G-HOTPART | the partition key must not be skewed; a read-heavy hotspot → replicas, not resharding | a skewed `partition_key`, or a read-heavy hotspot solved with hash+scatter-gather | partition-keys-and-hot-partitions | DET |
| G-PAYLOAD | large blobs go through an object store + URL, never through the app servers | an edge with `payload=large` whose destination is a `service` (≠ object_store), or a blob inline in the metadata DB | keep-large-payloads-out-of-path | DET |
| G-ASYNC | persist+ack immediately, propagate/replicate async; no synchronous fan-out before the ack | the ack depends on the fan-out/replication completing | decouple-with-async-propagation | DET+ADV |
| G-LEVER | do not pay for a guarantee the requirement does not demand (strong consistency, a live index, an exact count) | the design pays for a guarantee stronger than the requirement tolerates (e.g. a live index where staleness is OK) | exploit-tolerated-weakness | ADV |
| G-NAIVE-FIRST | there is ≥1 naive alternative discarded with its failure named before the chosen one | a final design with no alternative considered/rejected with a reason | iterate-naive-to-optimal | ADV |
| G-OLTP-OLAP | analytical reads / full scans / group-bys do not run on the operational store; analytical/training data leaves via CDC to a warehouse/lake | there is an analytical/ETL/batch query against the serving store (OLTP), or a single store serving OLTP+OLAP | separate-operational-from-analytical | DET+ADV |
| G-TWO-STAGE-RANK | when there is ranking/recommendation over many candidates, generate cheap candidates before the expensive ranking (avoid O(N) at runtime) | pairwise/pointwise ranking at runtime against the whole set, with no cheap candidate-generation stage | ml-system-design | ADV |
| G-MODEL-PERSIST | a trained model is persisted in a model store and served from there; it never lives only in the session and is never deployed directly onto the serving machine | the model is kept in session/ephemeral, or deployed directly without a store, or the model's I/O is not declared | ml-system-design | DET+ADV |
| G-PERSIST-BEFORE-VISIBLE | persist durably before making an effect visible to third parties (broadcast/fan-out/200 OK) | broadcast/publish/ack to other users before the data is durable in the store (a crash between steps loses/exposes data) | persist-before-external-visibility | DET+ADV |
| G-DELTA-NOT-STATE | at scale, propagate changes (deltas) and not constant state; and send id+refetch instead of the payload through the broker | broadcast of constant state/heartbeat to a large group, or a large payload travelling through the broker instead of an id | model-invariants-in-data | DET+ADV |
| G-INVARIANT-IN-DATA | domain invariants are guaranteed by the data model (money is not a float; counts are non-negative; a timestamp instead of a boolean to detect staleness) | money as a float; a counter that can go negative without a guard; a boolean where a timestamp is needed | model-invariants-in-data | DET |
| G-NO-CLIENT-TRUST | security/correctness enforcement is server-side; the client neither decides nor filters what is sensitive | rate limiting/authorization/filtering of sensitive data in the browser; an id/shard/timestamp chosen by the client (spoofable, DDoS) | enforce-on-the-server | DET+ADV |
| G-APPEND-ONLY | where there is auditing/state reconstruction or an LSM store, prefer append-only/event sourcing over in-place update/delete | in-place update/delete on an LSM store (tombstones); state that must be reconstructible but has no event trail | append-only-event-sourcing | ADV |
| G-NO-DUAL-WRITES | do not write to two stores on the creation path; synchronize the second one via CDC | a synchronous dual write to two stores before responding (partial failure) | separate-operational-from-analytical | DET |
| G-COLD-START | (ML/recsys) handle cold-start and explore/exploit, or scope them out explicitly | a recsys/ranking with no mention of cold-start at all; using the domain as a cop-out to ignore it | ml-system-design | ADV |
| G-NO-OVERENGINEER-REALTIME | do not add real-time/stateful machinery (WebSocket/SSE) when access is intermittent | a persistent/stateful connection where the user does not watch continuously (polling/reload is enough) | classify-workload-first | ADV |
| G-CACHE-POPULAR-NOT-ALL | cache/CDN only the hot subset (via a popularity batch); do not push everything | trying to put the whole dataset in the CDN/cache instead of the popular part | exploit-tolerated-weakness | ADV |
| G-MATERIALIZE-TECH | every component names a concrete technology justified by the shape of the access (principle→materialization) | a component left as a generic abstraction ("durable log"/"object store") with no named tech, or a tech not tied to the access pattern | materialize-tech-choices | DET+ADV |
| G-ENUMERATE-VARIATIONS | name the problem's axes of variation and draw the distinct variations (or justify collapsing them) | a single design where the problem has 2+ regimes (strong×eventual, fixed×dynamic, continuous×intermittent) without the axes exposed | enumerate-variations | ADV |
| G-ML-FEATURE-ENG | (ML) survey of algorithms by available data; real feature engineering (dimensionality reduction, text encoding, normalization); model chosen by the shape of the output, baseline-first; offline training in the warehouse | raw high-dimensional features with no reduction; skipping the algorithm survey; training/feature engineering on the serving OLTP; no baseline before the complex model | ml-system-design | ADV |
| G-DOC-LEGIBLE *(runs in the publish phase)* | the figures go from the high level to the detail and each one is legible on its own: there is a context view, no figure has more than ~10 boxes, and there is a sequence diagram for each main flow | the context view is missing; some figure is a tangle (>~10 boxes) instead of becoming a zoom; or there is no sequence showing order/asynchrony | decompose-diagram-for-teaching | DET+ADV |
| G-DOC-PEDAGOGIC *(runs in the publish phase)* | the document explains the capacity/demand NFRs in plain language (naming the binder and the calculation), and each design decision comes with the rejected naive alternative; every figure is followed by prose that reads it | capacity NFRs given only as raw numbers with no explanation; the binder not named; a decision with no rejected alternative; an orphan figure (no text) | decompose-diagram-for-teaching | ADV |

> The catraca principle: a gate only counts as installed after it has been **seen to fail**
> a provoked violation. Validation by mutation: inject the anti-pattern into the design (swap
> a strong store for an eventual one, a skewed partition key, remove the idempotency persist)
> and confirm that the corresponding gate goes RED.
